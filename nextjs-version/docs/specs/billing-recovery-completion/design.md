# Billing recovery completion — design amendment

Status: design approved by the user in conversation. Billing policy approved on 2026-09-21.
This is a brownfield amendment to the deployed subscription implementation.

## Approved policy references

- R1: Preserve outstanding debt and charge missed subscription months during suspension
  until the subscription's effective cancellation date.
- R2: Suspend business access and outbound automation seven days after the original
  unpaid renewal; retries and payment-method updates cannot reset the deadline.
- R3: Allow at most 48 additional hours when verified processing payments cover all
  overdue debt. Failed or action-required payments do not qualify. No repeated extensions.
- R4: Restore eligible access only after verified full payment, preserving manual
  suspensions, legacy exemptions and durable outbound reapproval boundaries.
- R5: Retain billing/payment and cancellation access during suspension; disclose ongoing
  fees, outstanding invoices and the recovery requirement to company administrators.
- R6: Validate real Stripe behavior in the authorized FundLane sandbox before live rollout.

## Current state and gaps

`billing-reconciliation.ts` pauses future collection using `keep_as_draft` but does
not disable retries on already-open invoices. It excludes draft invoices from debt,
so paying an old invoice can restore access despite unpaid missed-month drafts.
Processing eligibility is a customer-wide boolean, rather than proof that every
overdue invoice has enough money processing. Clearing the extension field also
loses evidence that an extension was already granted during that delinquency episode.

`billing.ts` already uses signed, deduplicated webhooks, verified provider reads,
pending seat increases and scheduled reductions. These remain the integration points.
Stripe's planner recommends hosted Checkout; its accepted guide and source review
are in `../../stripe-integration-review.md`.

## Reconciliation design

Keep Stripe invoices as the monetary source of truth: no hand-calculated catch-up
invoices and no second subscription to collect arrears. Scope billable invoices to
verified Fundlane subscription IDs owned by the mapped customer, including canceled
historical subscriptions with outstanding debt. Standalone invoices and unrelated
subscriptions must not be mutated by recovery.

At the collection cutoff, persist the access boundary and pause future collection.
Independently disable `auto_advance` on relevant open invoices. Recheck this invariant
on every reconciliation, including after a partial provider success/local rollback.
Already-dispatched processing payments cannot be recalled by these updates.

For each missed-period draft generated by the paused subscription, finalize it with
`auto_advance: false`. This preserves the original Stripe-calculated price, seats and
period, makes the debt payable using its hosted invoice page, and avoids an automatic
catch-up charge. Only finalize renewal drafts for already-started periods during a
recorded collection pause; never finalize unrelated or normal pre-renewal drafts.
Track applicable drafts as unresolved debt even when finalization fails.

Provider mutations use deterministic operation keys and fresh provider-state checks.
Recovery repeats invoice reads after finalization; clearing local delinquency requires
no outstanding applicable drafts, open invoices or uncollectible debt, and confirmed
settlement of the original delinquent invoice. A void/write-off is not payment.
Unsetting collection pause resumes future billing only. A canceled subscription
stays canceled; debt payment alone cannot recreate service.

_Requirements: R1, R2, R4, R5._

## Processing extension

Build a per-invoice coverage map from current Stripe InvoicePayment/PaymentIntent
records. Validate invoice, customer, currency, allocation and current processing
status; deduplicate intents and avoid counting the same allocation twice. Every
overdue invoice's remaining amount must be covered. Unknown or unsupported allocation
information fails closed for extension eligibility.

Grant the exception only before the seven-day cutoff; it must not reopen a company
that has already reached suspension. Fix its deadline at original grace end plus
48 hours. Reconciliation revokes active extension eligibility if coverage disappears
or a payment fails. Keep a durable granted-at marker until that delinquency episode
is fully resolved, preventing a second extension after revocation.

Add an additive migration, leaving deployed migration 0047 unchanged:

```sql
ALTER TABLE company_subscription_state
  ADD COLUMN processing_extension_granted_at text;
UPDATE company_subscription_state
SET processing_extension_granted_at = updated_at
WHERE processing_extension_until IS NOT NULL;
```

Local API/worker access gates continue checking absolute deadlines without network
calls. Provider failures fail closed for new recovery/extension grants. Failures that
arrive asynchronously are enforced when observed by webhook or reconciliation; a
cached processing exception can never exceed its fixed 48-hour deadline.

_Requirements: R2, R3, R4._

## Billing presentation and interfaces

Extend existing billing data with a server-derived recovery projection:

```ts
type BillingRecovery = {
  overdueAmount: number; // cents, USD Fundlane catalog
  paymentRequired: boolean;
  verificationPending: boolean;
  invoices: Array<{
    id: string;
    status: string;
    amountRemaining: number;
    periodStart: string;
    periodEnd: string;
    hostedInvoiceUrl: string | null;
  }>;
};
```

Use existing Plans & Billing components and authorization. Present each unpaid
invoice with its Stripe-hosted payment link. The aggregate is informational;
Stripe confirms payment per invoice. Show verification-pending state after payment
instead of trusting the redirect. Payment/cancellation remain accessible when paused.
Add ongoing-fee and cancellation language to existing billing and suspension notices.

_Requirements: R1, R4, R5._

## Stripe integration improvements

Explicitly request flexible billing on new hosted Checkout subscriptions and add a
stable flow-specific integration identifier. Verify compatibility with pending
updates, supported payment methods and schedules in the sandbox before deployment.
Do not migrate existing subscriptions implicitly. Verify catalog and Portal settings
in the authorized sandbox; application API credentials remain separate from MCP OAuth.

Tax collection requires the merchant's registrations/settings before activation.
Live Stripe, Google OAuth and email delivery require their corresponding provider
credentials/configuration and acceptance. Track those separately from code completion.

_Requirements: R6._

## Verification and rollout

Database-backed regressions cover multiple unpaid months, partial payment, processing
coverage shortfalls, extension revocation/retry, cutoff boundary timestamps, canceled
subscriptions, unrelated invoices, repeated events, provider failure after partial
success, manual suspension and stale outbound approvals.

Sandbox acceptance uses synthetic companies, a disposable database and Stripe test
clocks. Verify invoice finalization produces payment links without auto-charging,
old-invoice retries stop, missed-month invoices remain payable, partial settlement
cannot restore access, and full settlement resumes eligible service.

Run full regression tests, typecheck, lint and production build; refresh Graphify.
Apply the additive migration before deploying compatible code. Record source revision,
deployment, migration evidence and provider results distinctly. Existing production
companies retain their legacy access until explicit paid conversion.

_Requirements: R1, R2, R3, R4, R5, R6._
