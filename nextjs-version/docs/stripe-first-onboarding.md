## Selected lifecycle

Login remains separate from Get Started. A new customer opens pricing and Stripe Checkout without a Fundlane account, company or seat form. Stripe collects email, business name and card for one base user at the validated catalog price, USD 399 per month. Checkout creates the subscription and starts exactly 14 provider days when the purchase completes. Merely opening Checkout starts no local trial. Unless canceled, the subscription converts automatically; additional seats are managed later inside the app.

Signed events are retained and reconciliation re-fetches the exact account, mode, Checkout request/generation, customer, subscription, price, quantity, card and trial dates. Provider work runs outside database transactions. A verified, live Supabase identity and normal MFA are still required to claim. Claim creates company, membership, owner, billing projection and SMS association atomically. Stripe's original dates remain authoritative through delayed return, cross-device recovery, retries and rollback.

Accepted activation creates two independent service-email intents: `business_information_requested` and `getting_started`. Neither is an authentication credential or a membership grant. Supabase security email has its own provider configuration. Business details, internal review, invitations, setup checklists and mail delivery do not gate CRM. EIN belongs only in the protected, company-bound encrypted form; never request it by email reply.

Known trial ineligibility is explicit and never silently becomes immediate paid Checkout. Existing companies and subscriptions remain intact. Exact redundant uncharged trials may be compensated only under the reviewed rules; ambiguous history or conversion requires operator evidence.

Pending Checkout status has no locator-targeted start capability. A return or cross-device view must wait, retry its status read or contact support while the original request is unresolved; it must not start a second enrollment to recover that purchase. Completed, accepted enrollments support authenticated cross-device claim and billing recovery. This practical pending-purchase limitation must remain visible in the public integration's copy and tests.

## Operator diagnostics

`/platform/onboarding` and `GET /api/platform/onboarding` use the existing real super-admin grant, confirmed provider identity and same-session MFA. Company roles and API keys cannot grant access. The diagnostic list stays readable when onboarding runtime is disabled so operators can inspect retained history during rollback. Provider work and mutations retain their own runtime and fresh-action gates.

The SQL-only list selects enrollment age/state, revision, workspace locator, trial end, last verification, next repair, lease deadline, a repair-error boolean and each current service-mail generation's state/attempt count. It never selects contact details, EIN, hashes, ciphertext, secrets, challenge tokens, mail content, purchase evidence or raw provider errors/payloads. Filters run before a bounded limit of 1–100; the default page is 50. A creation-time/ID cursor is bound to the enrollment and state filters.

Repair observations distinguish attached history, operator holds, active leases, future work, due work and lease-free work overdue by at least 15 minutes. “Stalled” is a database age observation, not proof that a scheduler is absent. Runtime/creation/mail flags describe the current application process, not the scheduler's configuration. `accepted` is provider acceptance evidence, not receipt; `uncertain` requires evidence before replay. Empty results or zero counters are not delivery proof.

The page subscribes to the platform's existing visible-tab 30-second refresh event and adds no timer. Same-query refresh failures retain a marked stale snapshot; denied access discards it. Changing filters resets pagination and does not show data from a different query. Refresh preserves draft filter values. Inspecting a row reads the protected SQL detail projection: original trial end, saved provider association, latest target verification and separate mail generations/receipts. Saved provider observations are not a new provider read; transport configuration identity remains explicitly unverified.

The detail offers only the reviewed `verify_target`, `approve_identity`, `record_email_evidence` and `reissue_emails` POST actions. Operators explicitly open a draft, supply a bounded opaque independent case reference and reason, verify an authenticator code through the existing same-session step-up endpoint, and submit. Target verification uses the target's normal email verification; approval uses the latest inspected verified provider identity and a new operator step-up. Reissue requires the independently approved purchase reference and another new step-up after approval or a prior reissue. These controls neither confirm Auth accounts nor merge identities, transfer ownership, repair credentials, clear safety suppression or replay uncertain mail.

Each draft retains its inspected revision and exact target/mail/configuration/message binding. A refresh can update diagnostics but cannot retarget the draft. Changed revisions or bindings disable submission until the operator discards the old draft and inspects a new one. Same-query failures retain safe stale diagnostics with actions disabled; denied reads discard the detail and private draft. Explicit success/conflict rereads the current observations, with no automatic resubmission. Pending actions block duplicate clicks and queue selection changes. Known durable receipt message ownership is read-only even when the current message projection is absent; negative evidence cannot erase positive history. Runtime-off diagnostics remain readable with all recovery controls disabled.

Focused installed-Chrome coverage in `tests/browser/onboarding-operator/` renders the actual page/chrome/components against intercepted loopback APIs. It verifies all four exact action bodies, fresh draft step-up, receipt-owned identity, refresh/stale/denied/conflict/draft behavior, runtime rollback, selected-ID abort, filter/pagination, visibility refresh, labels, keyboard focus and 390/1440px light/dark rendering. Synthetic provider success does not replace the separate server authority tests or hosted receipt evidence.

## Runtime result interpretation

Enrollment maintenance defaults to at most 25 due, unclaimed rows, clamps its limit to 0–100 and uses a 20-second duration deadline. Future rows, active leases and operator-required rows are skipped. Pending/canceling/uncertain compensation follows its exact-subscription recovery path; other candidates reconcile. A disabled runtime returns zero work. A `repaired` counter means the maintenance operation completed; it is not a claim, paid entitlement or email-delivery assertion.

The comms owner calls `runOnboardingEmails` only with runtime and mail dispatch enabled. It uses at most 25 messages and a phase deadline 90 seconds before the unchanged 230-second comms deadline (at most 140 seconds), with the existing 20-second attempt guard. The reservation allows existing notification discovery (up to 15 seconds), the 60-second receipt-repair entry threshold, the 45-second send entry threshold, and overhead. Verify useful old notification and receipt progress alongside retained onboarding backlog before enabling both runtimes on the approved target; digest/webhook work also consumes the reserved interval. The result reports attempted/accepted/uncertain/suppressed, not received. Missing configuration can defer work with no provider attempt. A successful empty cron response must be recorded as disabled or no work according to flags and queue observations, never as delivered mail.
