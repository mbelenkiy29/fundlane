# Bounded scheduled funder reply polling

`runScheduledReplyIngest(clock, deadlineMs)` receives the comms scheduler's absolute remaining budget. Both `MCA_FUNDER_REPLY_LIVE_INGEST_ENABLED` and `MCA_FUNDER_REPLY_SCHEDULED_INGEST_ENABLED` must equal `true`; otherwise it returns without database or provider work. No schedule, credential or flag is installed by this change.

Each pass selects at most 25 workspaces with opted-in, verified submission senders. It processes one sender per workspace, oldest checkpoint first, using at most a 25-second execution slice and a two-message provider page. It stops starting slices with less than three seconds remaining and reserves one second for bounded cleanup. Existing database execution scopes cancel statements/lock waits. OAuth refresh, mailbox requests and configured AI classification share cancellation, including response-body reads. An AI timeout retains the existing labeled deterministic fallback; an expired execution cannot persist a fallback as completed work.

The existing mailbox checkpoint row stores a short token-fenced lease and rotates its timestamp **before** provider IO. Manual scans and scheduled ticks acquire the same lease, so they cannot process the same sender concurrently. Manual scans have a 230-second request budget, 25-second sender slices and at most 100 messages per provider page; they return a busy error when another scan owns the sender. A killed process has already rotated behind other workspaces/senders, and its lease expires after the slice plus five seconds. Cleanup removes only its own token; contention may leave the lease to expire. Non-deadline failures save a sanitized error code and attempt time through the same token fence. Current opt-in, runtime flags for scheduled claims, lease and company access are rechecked before provider work, including automatic classification. Opt-in control changes atomically modify only that flag and preserve current cursor, lease and pending IDs. Opt-out also deletes the active token/lease, so turning polling back on cannot reactivate a stopped worker. Stale progress/error writes cannot undo that control change.

A partial inbox checkpoint retains the original scan start/end, provider pagination state and unfetched provider IDs. Microsoft continuation URLs retain their original page size and remain opaque: resuming a manual 100-message page with a scheduled two-message limit returns only two messages and retains surplus IDs for bounded hydration, without storing message contents in the cursor. Completion advances to the original scan end, never the time a long resumed scan finishes. The existing 15-minute polling overlap and unique provider-message identity remain authoritative. The cursor advances only after every returned message has been persisted. A failure before that write replays the original page safely. Existing manual runs also understand these resumable cursors.

An individual retained-message GET returning 404 retires that missing identity so deletion between listing and hydration cannot pin the mailbox. Authentication, rate-limit, transient and execution failures preserve the cursor for retry. Each hydration pass counts missing messages against its request cap and advances the completed scan boundary only after the retained IDs are resolved.

Matched replies carry a private pending-preview marker in existing reply evidence before the inbox cursor advances. These reply rows form the durable queue; checkpoint pending IDs are only a bounded active-page diagnostic. Existing checkpoint-only intent is promoted when a sender is claimed. Each sender slice attempts at most two previews before its inbox page and two afterward, with a five-second sub-budget per drain inside the 25-second sender slice. An attempt rotates before classifier IO, so interruption cannot pin later work. Ordinary preview failures are audited with sanitized codes and remain pending for a later eligible actor; they do not prevent other previews or inbox polling. Expiry retains pending intent, and no pending ID is silently truncated from durable reply evidence.

Marker writes and automatic preview persistence lock and recheck the current sender token, opt-in and live lease. Automatic persistence rechecks company access after classification and loads fresh reply evidence under the reply lock; a concurrent broker preview or confirmation is reused. Standalone broker extraction retains its existing behavior. A stopped extraction resumes even when the reply already exists and the inbox cursor has advanced. Persisted previews are reused rather than classified again; confirmation and offer/deal mutation still require the existing broker review. AI selection retains the existing configuration. Internal queue markers are omitted from public reply evidence. Submission correlation keeps actual provider receipt identities available for domain/subject matching when the provider's real RFC Message-ID is unknown; it does not invent direct/thread evidence.

No migration is needed: the checkpoint, replies, restricted grants and extraction evidence use existing tables. Before activation, run the package-backed reply/provider tests with disposable PostgreSQL, verify the restricted runtime role, then use an approved synthetic nonproduction mailbox to check partial pages, concurrent ticks, disconnect/opt-out, killed polling/extraction, duplicates and useful progress for multiple workspaces. Native tests mock HTTP and database boundaries; they do not establish hosted OAuth access, provider delivery, real mailbox cursor validity, deployed scheduling or production readiness.
