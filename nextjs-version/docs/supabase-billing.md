# Supabase and Stripe company billing

Company billing now uses Stripe Checkout and Customer Portal. Supabase Stripe Sync Engine owns the private `stripe` schema. Application-owned `workspace_stripe_customers` maps immutable workspace IDs to Stripe customer IDs; `workspace_billing_entitlements` controls seat capacity. The original `workspace_billing` table and Clerk webhook history remain untouched historical records. Existing memberships and business access never depend on successful payment.

The test catalog is Free ($0, 1 seat), Starter ($49/month, 5 seats), and Team ($99/month, 20 seats), with one subscription item and quantity one per company. Both active and pending memberships occupy seats. Billing routes require a live admin or super-admin session; API keys cannot manage billing. Only `rk_test_` / `sk_test_` credentials, test customer/subscription/price objects, and test webhook events are accepted. A restricted key is preferred; grant the required customer, price, subscription, Checkout, and Billing Portal access.

## Environment and installation

Set server-only `MCA_STRIPE_BILLING_ENABLED=true`, `STRIPE_SECRET_KEY`, `STRIPE_STARTER_PRICE_ID`, `STRIPE_TEAM_PRICE_ID`, `STRIPE_BILLING_WEBHOOK_SECRET`, and the exact `MCA_APP_ORIGIN`. No Stripe secret belongs in a `NEXT_PUBLIC_` variable. Use independent sandbox catalogs and webhook endpoints in staging and production. This implementation intentionally remains test-only even on the production application.

1. In the intended Supabase project, install the dashboard Stripe Sync Engine integration in test mode. Enable syncing customers, products, prices, subscriptions, subscription items, and invoices. Keep its schema outside the exposed Data API schemas. Grant the dedicated application database role `USAGE` on `stripe` and `SELECT` on `stripe.subscriptions` and `stripe.subscription_items`; use owner-managed default privileges for future engine tables. Never grant browser roles access or let the application write the engine tables. The managed integration must receive its own Stripe webhook events.
2. Run `node --conditions=react-server --import tsx scripts/stripe/setup-catalog.ts` for a read-only catalog inspection. Add `--apply` to create missing test products/prices, then set the returned price IDs in the server environment. Existing mismatched prices cause a stop instead of being overwritten.
3. Configure a dedicated **test-mode** Stripe Customer Portal and set `STRIPE_BILLING_PORTAL_CONFIGURATION` to its ID: invoice history and payment-method updates enabled; cancellation effective at period end; subscription changes allowed only between the two configured fixed monthly products/prices, quantity changes disabled. This preserves the account's default portal configuration. The UI sends already subscribed companies to this portal, preventing duplicate subscriptions. Without the optional configuration ID, Stripe uses the account default, which must enforce these same restrictions.
4. Add a separate Stripe endpoint at `${MCA_APP_ORIGIN}/api/webhooks/stripe`, signing secret in `STRIPE_BILLING_WEBHOOK_SECRET`. Deliver `customer.subscription.*`, `invoice.paid`, `invoice.payment_failed`, `invoice.payment_action_required`, `invoice.updated`, `checkout.session.completed`, `checkout.session.async_payment_succeeded`, `checkout.session.async_payment_failed`, and `checkout.session.expired` events. The endpoint validates the original request bytes and timestamp signature; duplicate receipts are transactional and failures remain retryable. Do not route this endpoint through browser authentication.
5. Run `node --conditions=react-server --import tsx scripts/stripe/reconcile-billing.ts` to inventory mappings. Add `--apply` for initial/free entitlement initialization or operator recovery. This does not migrate historical Clerk subscriptions or charge existing companies.

The Stripe Sync Engine was transferred to Stripe; the Supabase dashboard integration remains the supported installation path. Installation and credentials must be verified in the actual target project before deployment; repository code alone cannot provision that integration.

## Reconciliation and HTTP contract

- `GET /api/billing` returns enabled/testMode, local plan state, occupiedSeats, and canManagePayment. Admin-only.
- `POST /api/billing/sync` reconciles the active company, returning the same shape. Reads the Sync Engine snapshot and verifies current Stripe state before capacity changes. Delayed or out-of-order snapshots cannot grant seats. No customer means Free; it never invents a customer from an email match.
- `POST /api/billing/checkout` accepts `{ "planSlug": "mca_starter_test" | "mca_team_test", "onboarding"?: boolean }` and returns `{ "url": string }`. Validates actual test price amount/currency/interval, creates a customer mapped by workspace ID, and reuses pending sessions. Checkout metadata is traceability, not authorization. Return URLs derive only from configured origin; the success page cannot grant seats.
- `POST /api/billing/portal` accepts `{ "onboarding"?: boolean }` and returns `{ "url": string }`. Uses the active workspace's customer mapping and verifies its provider metadata.
- `POST /api/webhooks/stripe` reconciles lifecycle changes against live Stripe rather than trusting event order or event-reported entitlements.

Invitations check verified billing capacity in the same workspace-locked database transaction that inserts the pending reservation. Past-due/unpaid/paused subscriptions block new invitations while retaining all current records and memberships. Scheduled cancellations retain seats while Stripe reports active; immediate/finished cancellations revert capacity to Free. Downgrades never deactivate over-cap users. Provider outages preserve cached state and block new grants until verification recovers.

## Verification and operations

`MCA_TEST_DATABASE_ADMIN_URL=... node --experimental-test-module-mocks --conditions=react-server --import tsx --test tests/billing.test.ts` covers catalog/test-mode enforcement, signed/tampered/duplicate webhooks, receipt rollback, stale sync snapshots, canceled/incomplete/delinquent subscriptions, customer isolation, retained Clerk history, atomic parallel reservations, Checkout reuse, and Portal mapping. Use an isolated database only.

For staging acceptance, complete a test Checkout; verify local plan changes without waiting for Sync Engine; replay and delay events; cancel in Portal; fail a renewal; and concurrently invite more than the tier limit. Confirm the sync engine catches up and reconciliation source becomes `sync_engine`. Observe webhook 5xx/signature failures, reconciliation source, sync delay, provider exceptions, and over-cap company counts. Maintain a scheduled operator reconciliation to recover missed webhooks after an incident; event delivery is required, not optional.

A synthetic Starter subscription granted 5 seats using verified Stripe API state; within approximately five seconds the engine caught up and reconciliation reported `sync_engine`. Scheduled cancellation retained 5 seats, and immediate cancellation returned Free/1. The synthetic subscription was canceled. Dedicated Fundlane test prices, Portal configuration, and a separate application webhook were configured without changing the account's default Portal or creating live charges.
