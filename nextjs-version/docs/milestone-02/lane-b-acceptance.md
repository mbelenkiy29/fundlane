# Lane B acceptance — authenticated intake and connectors

Verified September 8, 2026. This report covers MIC-152, MIC-175, MIC-186, MIC-181, MIC-183, MIC-159, MIC-184, and MIC-176. “Local” means implementation plus deterministic fixture evidence; it does not mean the customer’s provider account or production delivery path has been configured.

## Frozen contract and durable behavior

`src/lib/mca/intake/contracts.ts` publishes the frozen `NormalizedIntakeInput`, `IntakeResult`, and state union. `ingestApplication(actor,input)` is implemented in `src/lib/mca/intake/service.ts`.

- Intake events persist before deal creation in a workspace-scoped SQLite ledger. The normalized application body is encrypted at rest.
- Uniqueness is exactly workspace + provider + provider event ID. Canonical payload checksums allow identical retries and reject a changed payload under the same event ID.
- Deal idempotency keys hash the complete provider/event pair. Long IDs with the same prefix cannot collide.
- A failure between deal creation and intake reconciliation is recoverable because both layers keep stable independent retry identities; no nested deal transaction is used.
- A replay with an existing deal rechecks the current actor’s deal visibility before returning its identifier.
- Attachments have an independent durable checkpoint (`pending`, `fetching`, `retryable`, `stored`, `failed`), exponential retry schedule, five-attempt terminal state, and readiness-summary recomputation after late files. Workers acquire expiring tokenized claims atomically; expired work can be reclaimed and token-CAS completion prevents a stale worker from overwriting the retry.
- Private retrieval requires HTTPS and an exact configured host, rejects embedded credentials, private/literal/resolved addresses and redirects, and enforces 15-second/25-MiB defaults while streaming.
- Scheduled workers accept either a scoped administrator session or `MCA_INTAKE_WORKER_TOKEN`; administrator execution is restricted to that administrator’s workspace.

## Provider contracts researched and implemented

Only provider-specific documented admission and payload contracts are used.

- Jotform: API-key/private-read behavior comes from [Jotform API documentation](https://api.jotform.com/docs/). Authenticated delivery uses the native Jotform Workflows Webhook element, whose [current setup guide](https://www.jotform.com/help/how-to-create-a-webhook-in-jotform-workflows/) documents configurable HTTP headers. The generated MCA bearer value must be placed in that workflow's `Authorization` header. The basic Form Builder webhook only accepts an endpoint URL and is not claimed as authenticated. A separate customer API key is used for private submission/file reads.
- Fillout: official webhook setup and optional authorization header from [Send form submissions to a webhook](https://www.fillout.com/help/webhook), and question/url-parameter submission shape from [Create submissions](https://www.fillout.com/help/api-reference/create-submissions). The connector uses a configured bearer secret and a separate private-read token.
- HighLevel: current `X-GHL-Signature` Ed25519 verification and published public key from the [Webhook Integration Guide](https://marketplace.gohighlevel.com/docs/webhook/WebhookIntegrationGuide/). The legacy RSA path was not added because the official deprecation date was September 1, 2026. `webhookId`, `locationId`, contact/custom fields, source, and assigned-user mapping remain provider-specific.
- DocuSeal: timestamped HMAC-SHA256 over `timestamp.raw_body` from [Use Webhooks](https://www.docuseal.com/resources/use-webhooks), plus distinct form/submission event semantics from the [DocuSeal API reference](https://www.docuseal.com/docs/api). Only `submission.completed` creates a final signed application; `form.completed` is deliberately acknowledged as incomplete semantics. Unknown templates enter review.
- Zoho Forms: the delegated product decision selects persisted contract `zoho_forms_json_drive_v1` with JSON, named top-level fields, and MCA bearer admission. Only explicit `entryId` is accepted as the configured Zoho Unique ID. `applicationFile` and `statementFile` accept only documented Google Drive file links, which are converted to Drive v3 media URLs; the encrypted Google OAuth token is sent only to `www.googleapis.com`. Unknown custom contract keys remain `pending_customer_contract`. This follows [Zoho webhook configuration](https://help.zoho.com/portal/en/kb/forms/integrations/webhooks/articles/webhook-configuration), [Zoho Unique ID](https://help.zoho.com/portal/en/kb/forms/field-types/form-fields/identifier/articles/unique-id), [external attachment storage](https://help.zoho.com/portal/en/kb/forms/form-settings/submissions-storage/manage-form-attachments/articles/save-attachments-in-google-drive), and [Google Drive media download](https://developers.google.com/workspace/drive/api/guides/manage-downloads).
- Custom webhooks use an explicitly documented MCA JSON shape and configured bearer secret. They do not borrow another provider’s signature or payload fields.
- Private email persists an explicit `postmark` or `custom` gateway. Postmark authenticates HTTP Basic before parsing and maps the documented `FromFull.Email`, `OriginalRecipient`, `MessageID`, `Headers`, body, and attachment fields. A valid original `Message-ID` header is preferred for deduplication; otherwise the Postmark callback ID is used. Attachment base64, declared/decoded length, individual size, and 25-MiB decoded aggregate are validated before deal creation; CID images are ignored while CID PDFs remain. The provider-verification path reads the actual Postmark server/address and configures its webhook only with supplied credentials and a deployed HTTPS origin; account tokens and credential-bearing hook URLs never enter status or logs. Custom email retains the prior MCA JSON/bearer contract only when explicitly selected. [Postmark inbound setup](https://postmarkapp.com/developer/user-guide/inbound/configure-an-inbound-server), [schema](https://postmarkapp.com/developer/webhooks/inbound-webhook), and [attachment parsing](https://postmarkapp.com/developer/user-guide/inbound/parse-an-email) are the source contracts.

All provider credentials and DocuSeal signing secrets are encrypted at rest. Bearer admission values are stored only as hashes. Admin APIs return a webhook secret only when created or rotated. Audits record IDs, provider, version, state, and correlation data; they do not record secrets, raw webhook bodies, document bytes, or application PII. The authenticated UI may show a submitted preview and a one-time generated secret to the administrator; neither is logged. Receipt workers also use expiring tokenized claims and send a stable `Idempotency-Key` derived from the durable receipt ID. A production receipt transport must enforce that key to suppress a duplicate after it accepted a request whose response was lost.

## Local acceptance evidence

`tests/intake-core.test.ts` passes 12 scenarios:

1. MIC-152 repeated delivery creates one deal, changed replay conflicts, and two 181-character-prefix event IDs create different deals.
2. MIC-152 existing-deal replay denies a different rep without visibility.
3. MIC-175/MIC-176 one Jotform plus two opaque links assigns the intended active reps; token tampering is quarantined and visible. A realistic file delivery creates its deal, retrieves the private statement with Jotform’s API-key header, stores it, and completes the checkpoint. The fixture sends the same bearer header required in the documented Jotform Workflow setup; it verifies the receiver contract without claiming a live Jotform delivery.
4. MIC-183 Fillout’s realistic question/file fixture creates the mapped assigned deal, fetches a private statement through bounded retrieval, stores it through the document service, and completes the checkpoint. MIC-186’s HighLevel fixture signs the raw request with Ed25519, preserves location/webhook/contact/tag mapping, assigns the external user, creates the deal, retrieves its private application, and stores the document. Production defaults to HighLevel’s published verification key; the fixture injects its own public verification key through configuration so it can prove the signature path without a live callback.
5. Provider mapping leaves missing/blank numbers unknown, maps two owners including numeric/boolean owner fields, and rejects owner targets beyond the bounded 0–9 indexes.
6. MIC-159 a signed DocuSeal HMAC fixture accepts `submission.completed` once, schedules and idempotently stores one signed PDF, ignores `form.completed`, and queues an unknown template for review.
7. MIC-181 the selected flat Zoho JSON fixture creates the expected business, owner, active-rep assignment, application, and statement. Identical replay is idempotent; changed replay conflicts; binding, identity, admission, and Drive-link errors fail deterministically. An expired Drive token leaves the file retryable, and rotation completes it on the original deal. An unknown contract key remains gated.
8. MIC-184 the explicit custom email gateway retains one-message behavior, signature filtering, extraction, assignment, PDF storage, receipt transport, and denied-sender review.
9. MIC-184 a genuine-shaped Postmark payload passes Basic admission, prefers the original Message-ID across two callback IDs, assigns the rep, retains two same-named PDFs with distinct identities, ignores the inline logo, queues one receipt, and covers denied auth/recipient/sender, malformed/mismatched/oversized attachments, extraction failure, forwarding-confirmation review, and provider-evidenced server/address setup without a real call.
10. MIC-152 private attachment tests deny a loopback target, redirects, streamed oversize data, and expired credentials.
11. MIC-152/MIC-184 parallel workers acquire one attachment/receipt claim, expired attachment and receipt leases are reclaimed, stale-token completions cannot overwrite the recovered result, and a lost receipt-provider response retries with the same stable transport idempotency key.
12. MIC-152 direct unauthenticated HTTP creation returns `401 authentication_required`; provider fixture delivery exercises admission credentials, and direct service plus authenticated route requests reject an unknown email gateway before it can bypass Postmark Basic.

UI coverage is in `IntakePanel()` and `/apply/[formId]`: loading, empty, validation/error, configured, custom-contract-pending, local-tested/live-unverified/live-configured readiness, activity, retry, credential/expiry rotation, selected Zoho named fields and Drive-token guidance, credential-dependent Postmark verification/provisioning, field-map fixture preview, receipt processing, and personal-link copy states are represented. The shared form page validates the opaque active-member/form binding before embedding Jotform and states the required statement, state selector, identifier/date, and identity-data expectations.
