## Metrics

Health is sampled every minute, not inferred from successful business requests. Availability is successes divided by observed samples. Missing samples are not claimed as uptime. Health is stale after three minutes. Query failures remain unavailable, never zero. Current queue/email cards are all-time/current-state snapshots; charts and usage use the selected UTC window. Submission counts cover tracked application invitations, not unrelated intake. Email acceptance does not prove delivery or inbox placement.

Document failure and scanner counts are zero while both document runtime flags are unset, and their owner dashboard alerts are hidden. When activating document consumption, set the selected existing flag (`MCA_DOCUMENT_JOB_RUNTIME=vercel_cron` or `MCA_NATIVE_DOCUMENT_EXECUTOR=true`) in both the web host and the Supabase `platform-monitor` function secrets. Values other than those exact strings remain disabled. Keep both unset to preserve the current production owner page. The heartbeat warning remains independently visible.

The Edge monitor keeps billing reconciliation incidents disabled by default. Set `MCA_BILLING_RECONCILIATION_ALERTS_ENABLED=true` in the Supabase function only after separately reviewing that alert behavior. A queued retry is still included in aggregate queue metrics while this alert is disabled.

Activity records one row per local user per UTC day and updates the last activity time on authenticated foreground API requests. GET endpoints also used for polling (session, jobs, mail, SMS, assistant, application lists, intake, calendar, senders), sync/status endpoints and automatic read receipts are excluded. Foreground mutations still count. Passive views of these polled screens are deliberately not claimed as engagement. This is API activity, not page views or complete analytics; read-only mailbox polling cannot establish active use. Collection is not backfilled. Existing invitation records supply real historical invitation counts.

Only allowlisted telemetry metadata is stored. Never pass exception messages, request bodies, SQL or provider payloads into event records. App errors always reach native logs; persistence runs with a separate single-connection pool and subsecond timeouts. Disable `MCA_OPERATIONS_ENABLED` to stop persistence without changing request behavior.

No runtime flags, secrets or schedules were changed by this audit.

Thresholds retain the documented defaults: three consecutive bad checks for health, expired leases, queue age **>600 seconds** and stale syncs; **five** provider/processing failures or reconnect-needed senders; **one** due retried billing notice. The existing configurable queue/provider thresholds also govern the new signals. Recent failures use ten minutes; email uses the worker-recorded `sync_error_at`, cleared on success. Calendar counts currently unhealthy connections (`error`/`reconnect`), clearing on successful sync. Email completion retains readiness’s ten-minute grace. Email stale sync counts verified merchant OAuth senders with conversations using their latest successful conversation sync, or first conversation creation if never synced, with a 30-minute grace (six worker cadences). An old conversation does not alert while its sender makes progress; disconnected senders and senders without conversations are excluded. Calendar last-sync checks retain ten minutes; the existing owner email card's five-minute stale count remains an earlier informational warning. The document heartbeat uses its existing 90-second configurable threshold. Three healthy checks recover an incident. Disabled runtimes are omitted, query errors produce unavailable metrics, and external alert outcomes remain accepted/rejected/unknown with no automatic unknown replay.

The coverage limits above require future worker instrumentation/acceptance, not invented success timestamps. Migration `0077_email_sync_error_time` adds nullable `mca_email_conversations.sync_error_at`; deploy it through the reviewed migration procedure before the updated messaging worker or enabling email recovery sampling. Historical errors remain null because their failure times are unknown. This migration was applied only to disposable test databases. ### Log hygiene evidence

The central unexpected-error serializer is `error-diagnostics.ts`; `errors.ts` passes its result to `operations/telemetry.ts`. The operational error table is **`mca_private.ops_errors`**, not `operational_errors`. Native diagnostics retain redacted/truncated messages, constructor/name classes, token-shaped codes/types, Stripe request IDs/params and HTTP status. Added message redaction covers Google/Microsoft OAuth token formats, labeled credentials/authorization, Twilio SIDs and labeled auth secrets, and bank/card digit runs. Stacks, causes, headers and arbitrary properties are not serialized. Telemetry retains syntax-constrained components/codes and unchanged correlation IDs so requests can be traced. Callers must supply identifiers, not sensitive payloads; pattern redaction does not promise detection of arbitrary unlabeled secrets or document excerpts.

`tests/operations-signals.test.ts` exercises real migrated Postgres and captures native error logs, recorded `ops_errors` rows, monitor aggregates, alert bodies and delivery-attempt rows with synthetic labeled credentials, authorization headers, full bank numbers and document content in excluded properties/stored business errors. Diagnostics tests preserve the original Stripe metadata/message expectations and exercise the added redaction formats. Worker tests verify sync failure timestamp recording and clearing; signal tests execute every runtime query with all runtime flags enabled against the migrated schema and verify sender progress, failure aging and recovery. Provider exceptions and stored business error text never enter alerts: payloads still contain only component, time, a fixed episode summary and dashboard URL. Transport authentication headers necessarily carry the configured transport credential; they are not log/alert-body content. All fetches in these tests are in-process mocks and send nothing. This is evidence for these central operational paths, not a claim to audit every legacy log or provider console.

## Failure and rollback

A full Supabase outage can stop custom checks and alerts. Email outages can prevent notifications. Consult Vercel/Supabase directly when samples are stale or the app cannot authenticate. Unknown/rejected notification outcomes are visible separately from business email state.

Disable only `fundlane-platform-monitor` with `cron.unschedule`, then set alerts and collection flags false and revoke the reviewed platform grant or narrow the super-admin ceiling if rolling back access. Retain all business records and additive operational tables. Native host logs remain available. No DNS or worker migration is part of this release.
