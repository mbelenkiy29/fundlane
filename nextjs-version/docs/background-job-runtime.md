## Retention holds (#46)

`MCA_RETENTION_HOLDS_ENABLED=true` enables platform-operator retention holds and makes assistant-file cleanup skip a workspace with an active company-wide hold. Unset, `false`, or any other value preserves the prior cleanup behavior and makes the hold API return 404. The API requires the existing platform-admin grant, MFA, and trusted mutation origin. Holds may target a company or one of its deals, use a controlled reason (`dispute`, `chargeback`, `subpoena`, or `regulator_request`), and require an operator note. Placement and release are recorded in `audit_events`; released rows remain as an immutable operational record. Deal-only holds are available for future deal-aware purge jobs, while the current assistant-file cleanup has only workspace ownership and therefore checks company-wide holds. No automated deletion of other business records or schedule is added here. Apply migration `0067_retention_holds` through the reviewed migration process before enabling the flag.

## Private email delivery consumer (#39)

`GET /api/cron/private-email` is a separate, opt-in Vercel Node consumer for `application_invitation_email`, `application_invitation_reminder`, and pending intake receipts. `MCA_PRIVATE_EMAIL_CRON_ENABLED=true` enables it; unset or any other value returns `{enabled:false}` without claiming work. Enabled calls require the existing `CRON_SECRET` bearer token, use a 100-second deadline, and process at most three invitation jobs plus three deliverable receipts. When `MCA_INVITATION_JOB_RUNTIME=vercel_cron`, this route stops claiming both invitation kinds even if its own cron flag remains on; it continues processing eligible intake receipts. An unset invitation runtime preserves the existing private-email claims. Receipt selection pages past undeliverable rows until it finds eligible work or reaches the 90-second work window. Invitation delivery also requires `MCA_APPLICATION_INVITATION_EMAIL_ENABLED=true`, `MCA_EMAIL_SENDER_VERIFIED=true`, an authenticated email webhook or exact-true credentialed transactional system provider; receipts require `MCA_PRIVATE_EMAIL_DELIVERY_ENABLED=true` and a configured outbound path: a verified useSend integration, the selected Resend system email transport with API key and From address, or a verified sender with both `MCA_INTAKE_RECEIPT_WEBHOOK_URL` and `MCA_INTAKE_RECEIPT_WEBHOOK_TOKEN`. The receiver must reject requests without the bearer token. Install a single `*/5 * * * *` Vercel schedule only after synthetic hosted acceptance. There is no repository cron entry. The provider receiver must deduplicate delivery IDs because lease recovery alone cannot prevent a duplicate send after a lost response.

Each general-runtime claim records a durable Vercel claim marker before outbound checks; a separate provider-attempt marker is written immediately before calling the email adapter. A queued retry with `providerAttempt: false` may proceed normally. ## Selected arrangement

Vercel Node owns a gated, bounded `/api/cron/jobs` consumer for private CSV export jobs, opt-in auto-submit scoring, and explicitly allowlisted business kinds. It uses the existing PostgreSQL queue: atomic `FOR UPDATE SKIP LOCKED` claim, ten-minute renewable lease, three attempts, token-fenced completion, and 30-second per-attempt backoff. The route limits each request to three jobs and 240 seconds under its 300-second maximum. `MCA_JOB_RUNTIME=vercel_cron` enables the consumer; unset is an authenticated-free no-op and preserves current behavior. `MCA_AUTO_SUBMIT_ENABLED=true` additionally permits `auto_submit` claims; unset or any other value leaves those jobs queued. `CRON_SECRET` authenticates enabled requests by constant-time bearer comparison. The route has no entry in `vercel.json`: an operator must install exactly one schedule after staging acceptance. The enqueue helper is enabled by `MCA_BACKGROUND_JOBS=enabled` **or** a truthy `VERCEL`; it does not activate this consumer. The export dispatcher cases currently have no in-repository production enqueue call; this route proves the runtime contract with an explicitly enqueued synthetic export, and #37 must connect reviewed export producers before claiming production coverage.

The active data plane remains Supabase Postgres, Auth, and private Storage. Vercel uses restricted pooled `DATABASE_URL`, `MCA_DB_POOL_MAX=2`, and no migration-owner credentials. The queue's unique `(workspace_id,kind,idempotency_key)` and lease token keep job identity stable across a killed execution. A stale worker cannot finish or fail the reclaimed row. Export service operations are idempotent by correlation ID or ready state; CSV results are private and authorized on retrieval. This is at-least-once execution; provider sends require their own receipt deduplication and must not be inferred safe from a database lease alone.

Auto-submit scoring can enqueue a separate `submission_delivery` job; the cron route claims it only when explicitly listed in `MCA_JOB_RUNTIME_KINDS`. The original outbound approval is carried into the submission queue, and the legacy worker continues to dispatch `auto_submit` through the same queue. Native scanning/PDF is absent from the Vercel allowlist. Outbound delivery and unproven large import/intake tasks are **not** selected by default. The existing documents Edge handler still returns 503 before claiming. The native path needs a non-Render container or a measured, resumable equivalent with ClamAV signature updates, Poppler, up to 25 MiB private files, scratch space, scanner verification, heartbeat, and a killed-execution retry proof on nonproduction Supabase. Do not enable an Edge documents schedule or promote unscanned files. `scripts/supabase/deploy.mjs` still gates production Edge deployment.
